 Kubernetes 1.32 | Rocky Linux 9.x | Ubuntu 22.04 GPU nodes
 Cilium | CRI-O | HAProxy x2 + Keepalived floating IP | etcd quorum

CLUSTER INVENTORY
--------------------------------------------------------------------

-------------------  --------------------  -------------  ----------  ---------------
Floating IP (VIP)    stage.proxyhost.lan   10.10.1.100    Proxy net   Keepalived VIP
HAProxy-1 (MASTER)   stage-proxy-host      10.10.1.36     Proxy net   Rocky Linux 9.x
HAProxy-2 (BACKUP)   stage-proxy-host-2    10.10.1.37     Proxy net   Rocky Linux 9.x
Control plane 1      isu-k8s-cp            172.18.0.101   On-prem ISU Rocky Linux 9.x
Control plane 2      stpi-k8s-master       172.26.0.8     On-prem STPI Rocky Linux 9.x
Control plane 3      gcp-k8s-master        10.10.1.26     Google Cloud Rocky Linux 9.x
CPU workers          <site>-k8s-wk-<n>     <worker-ip>    Any site    Rocky Linux 9.x
GPU workers          gpu-k8s-wk-<n>        <gpu-ip>       Any site    Ubuntu 22.04 LTS
 
NOTES
- All control planes are on DIFFERENT networks (cross-network) and
  connected over VPN. etcd quorum runs across the VPN.
- Public IPs are associated only with the HAProxy node(s) and the
  GCP control plane.
- The DNS name stage.proxyhost.lan ALWAYS points to the floating IP
  (10.10.1.100), never to an individual HAProxy node.
- The two HAProxy nodes must be in the SAME L2 segment so the floating
  IP can move between them. (If the proxies run inside GCP, VRRP
  floating IPs do not work natively; use alias IPs or a GCP internal
  load balancer instead.)
- Replace every IP, hostname and the interface name "eth0" with your
  own values.
- NEVER commit real join tokens, discovery hashes, certificate keys or
  kubeconfig files to a repository. Use placeholders and rotate
  anything that was exposed.

PHASE 1 - HAPROXY NODES (run on BOTH proxy nodes)
====================================================================
 
# dnf install haproxy keepalived -y
# cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg-original
 
Open the firewall for API traffic and VRRP between the two nodes:
 
# firewall-cmd --permanent --add-port=6443/tcp
# firewall-cmd --permanent --add-rich-rule='rule protocol value="vrrp" accept'
# firewall-cmd --reload
 
Add the local DNS entry pointing to the FLOATING IP:
 
# vi /etc/hosts
 
10.10.1.100 stage.proxyhost.lan
 
Edit /etc/haproxy/haproxy.cfg. The file is IDENTICAL on both nodes.
Keep the stock "global" section and replace the rest:
 
#---------------------------------------------------------------------
# Global settings (stock, keep as shipped)
#---------------------------------------------------------------------
global
    log         127.0.0.1 local2
    chroot      /var/lib/haproxy
    maxconn     4000
    user        haproxy
    group       haproxy
    daemon
 
    # utilize system-wide crypto-policies
    ssl-default-bind-ciphers PROFILE=SYSTEM
    ssl-default-server-ciphers PROFILE=SYSTEM
 
#---------------------------------------------------------------------
# Defaults
#---------------------------------------------------------------------
defaults
    mode                    tcp
    log                     global
    option                  tcplog
    option                  dontlognull
    retries                 3
    timeout connect         10s
    timeout client          1h
    timeout server          1h
    timeout check           10s
    maxconn                 3000
 
#---------------------------------------------------------------------
# Frontend: Kubernetes API
#---------------------------------------------------------------------
frontend k8s-api
    bind *:6443
    mode                tcp
    option              tcplog
    default_backend     k8s-control-planes
 
#---------------------------------------------------------------------
# Backend: round robin across the three control planes
#---------------------------------------------------------------------
backend k8s-control-planes
    mode        tcp
    option      tcp-check
    balance     roundrobin
    default-server inter 10s downinter 5s rise 2 fall 2 slowstart 60s maxconn 250 maxqueue 256 weight 100
    server isu-k8s-cp      172.18.0.101:6443 check
    server stpi-k8s-master 172.26.0.8:6443   check
    server gcp-k8s-master  10.10.1.26:6443   check
 
The 1h client/server timeouts keep long-lived kubectl sessions
(watch, logs -f, exec) from being cut by the proxy.
 
Check for syntax errors:
 
# haproxy -c -V -f /etc/haproxy/haproxy.cfg
 
Start and enable HAProxy:
 
# systemctl enable --now haproxy.service
 
If the service fails to start, check the logs and remediate:
 
# journalctl -xeu haproxy.service

PHASE 2 - KEEPALIVED FLOATING IP (run on BOTH proxy nodes)
====================================================================
 
/etc/keepalived/keepalived.conf on HAProxy-1 (MASTER, stage-proxy-host):
 
vrrp_script chk_haproxy {
    script "/usr/bin/systemctl is-active --quiet haproxy"
    interval 2
    weight -20
    fall 2
    rise 2
}
 
vrrp_instance K8S_API_VIP {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 101
    advert_int 1
 
    # Unicast VRRP works where multicast is blocked
    unicast_src_ip 10.10.1.36
    unicast_peer {
        10.10.1.37
    }
 
    virtual_ipaddress {
        10.10.1.100/24
    }
 
    track_script {
        chk_haproxy
    }
}
 
On HAProxy-2 (BACKUP, stage-proxy-host-2) use the same file with:
    state BACKUP
    priority 100
    unicast_src_ip 10.10.1.37
    unicast_peer { 10.10.1.36 }
 
# systemctl enable --now keepalived
 
Verify (the VIP must appear on the MASTER only):
 
# ip addr show eth0 | grep 10.10.1.100
 
Test failover:
1. Stop HAProxy on the MASTER:   systemctl stop haproxy
2. Confirm the VIP moved to the BACKUP: ip addr show eth0 | grep 10.10.1.100
3. Confirm the API port still answers:  nc -zv stage.proxyhost.lan 6443
4. Start HAProxy on the MASTER again and watch the VIP fail back.

3.1 Hostname (set it ONCE, do not change later)
--------------------------------------------------------------------
 
# sudo hostnamectl set-hostname <control-plane/worker-hostname-here>

NOTE: If you change the hostname later, the node will not rejoin
automatically after a stop/reboot or maintenance, and kubelet logs
show errors like:
 
  node "old-name" not found
  User "system:node:old-name" cannot get resource "leases" ...
  can only access node lease with the same name as the requesting node
 
See FAILURE CASE 2 if this happens.

PHASE 4 - INITIALIZE THE FIRST CONTROL PLANE (isu-k8s-cp)
====================================================================
 
The control plane endpoint is the KEEPALIVED FLOATING IP (via its DNS
name), not an individual HAProxy node. Run on ONE control plane only:
 
# sudo kubeadm init \
    --skip-phases=addon/kube-proxy \
    --control-plane-endpoint "stage.proxyhost.lan:6443" \
    --apiserver-cert-extra-sans "10.10.1.100,stage.proxyhost.lan" \
    --upload-certs
 
kubeadm downloads the required images. Verify with:
 
# crictl images
 
Sample (versions will match your cluster):
IMAGE                                     TAG
registry.k8s.io/coredns/coredns           v1.11.x
registry.k8s.io/etcd                      3.5.x-0
registry.k8s.io/kube-apiserver            v1.32.x
registry.k8s.io/kube-controller-manager   v1.32.x
registry.k8s.io/kube-scheduler            v1.32.x
registry.k8s.io/pause                     3.10
 
SAVE the join output (it is shown only once). Example shape:
 
  kubeadm join stage.proxyhost.lan:6443 --token <token> \
      --discovery-token-ca-cert-hash sha256:<hash> \
      --control-plane --certificate-key <cert-key>
 
  kubeadm join stage.proxyhost.lan:6443 --token <token> \
      --discovery-token-ca-cert-hash sha256:<hash>
 
The certificate key gives access to sensitive cluster data, keep it
secret. Uploaded certs are deleted after 2 hours. Reload them with:
 
# kubeadm init phase upload-certs --upload-certs
 
Join tokens expire after 24 hours. Create a new one with:
 
# kubeadm token create --print-join-command
 
Prepare a normal user to reach the API:
 
$ mkdir -p $HOME/.kube
$ sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
$ sudo chown $(id -u):$(id -g) $HOME/.kube/config
 
Optional warnings you may see:
- "kernel release 5.14.x is unsupported" on Rocky 9: this is a
  SystemVerification warning and can be ignored.
- "sandbox image pause:3.10 inconsistent with kubeadm": optionally set
  the CRI-O pause_image to the version kubeadm recommends.

PHASE 5 - JOIN ADDITIONAL CONTROL PLANES AND WORKERS

5.1 Join the 2nd control plane (stpi-k8s-master), different network:
 
# sudo kubeadm join stage.proxyhost.lan:6443 \
    --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash> \
    --control-plane \
    --certificate-key <cert-key>
 
5.2 Cross-network etcd SANs (do this BEFORE joining the 3rd control
plane). Take a backup of the etcd PKI:
 
# sudo cp -r /etc/kubernetes/pki/etcd /etc/kubernetes/pki/etcd.backup.$(date +%Y%m%d)
 
Then add the control-plane IPs to the etcd SAN lists by editing the
EXISTING ConfigMap in place (do not replace it with a partial file):
 
# kubectl -n kube-system edit cm kubeadm-config
 
Under ClusterConfiguration, set:
 
etcd:
  local:
    serverCertSANs: ["localhost", "127.0.0.1", "172.18.0.101", "172.26.0.8", "10.10.1.26"]
    peerCertSANs:   ["localhost", "127.0.0.1", "172.18.0.101", "172.26.0.8", "10.10.1.26"]
 
5.3 Join the 3rd control plane (gcp-k8s-master):
 
# sudo kubeadm join stage.proxyhost.lan:6443 \
    --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash> \
    --control-plane \
    --certificate-key <cert-key>
 
5.4 Join worker nodes (CPU and GPU pools):
 
# kubeadm join stage.proxyhost.lan:6443 \
    --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash>
 
5.5 Verify:
 
# kubectl get nodes -o wide

PHASE 7 - PERSISTENT STORAGE
====================================================================
 
Choose ONE option below. Do not create two StorageClasses with the
same name.
 
--------------------------------------------------------------------
Option A - Local path provisioner (dynamic local disks)
--------------------------------------------------------------------
 
Pin the manifest to a release tag instead of "master" so installs are
reproducible (see https://github.com/rancher/local-path-provisioner/releases):
 
# kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/<release-tag>/deploy/local-path-storage.yaml
 
# kubectl get pods -n local-path-storage
# kubectl get sc
 
Output:
local-path   rancher.io/local-path
 
By default PV directories are created on the node where the pod is
scheduled, under /opt/local-path-provisioner/ (one PVC = one directory).
 
# kubectl get configmap local-path-config -n local-path-storage -o yaml
 
Change the host path (RECOMMENDED): do not use /opt, use a dedicated
disk or directory, for example /var/lib/k8s.
 
Step 1 - create the directory on ALL worker nodes:
 
# mkdir -p /var/lib/k8s
# chmod 755 /var/lib/k8s
 
Step 2 - edit the ConfigMap:
 
# kubectl edit configmap local-path-config -n local-path-storage
 
data:
  config.json: |
    {
      "nodePathMap":[
        {
          "node":"DEFAULT_PATH_FOR_NON_LISTED_NODES",
          "paths":["/var/lib/k8s"]
        }
      ]
    }
 
Step 3 - restart the provisioner:
 
# kubectl rollout restart deployment local-path-provisioner -n local-path-storage
 
Step 4 - create the StorageClass:
 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: stage-storage
provisioner: rancher.io/local-path
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Retain
 
--------------------------------------------------------------------
Option B - NFS provisioner
--------------------------------------------------------------------
 
# helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner
# helm repo update
 
# helm install nfs-provisioner nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
    --set nfs.server=<NFS_SERVER_IP> \
    --set nfs.path=/nas \
    --set storageClass.name=stage-storage \

The chart already creates the StorageClass. Only create one manually
if you need custom settings (use a different name or delete the chart's
class first):
 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: stage-storage
provisioner: cluster.local/nfs-provisioner-nfs-subdir-external-provisioner
parameters:
  archiveOnDelete: "true"
reclaimPolicy: Delete
volumeBindingMode: Immediate
allowVolumeExpansion: true
 
Note: install the NFS client packages on every node that mounts NFS
(Rocky: dnf install nfs-utils, Ubuntu: apt install nfs-common).

            limits:

FAILURE CASE 1 - STALE ETCD MEMBER (CONTROL-PLANE REJOIN)
====================================================================
 
Symptom: a control plane was rebuilt or re-provisioned, and rejoin
fails at the check-etcd phase:
 
  error execution phase check-etcd: etcd cluster is not healthy:
  failed to dial endpoint https://172.18.0.101:2379 with maintenance
  client: context deadline exceeded
 
Diagnosis: the existing etcd cluster still lists the old member
(isu-k8s-cp, 172.18.0.101) as "started", but it is dead. etcd
membership is authoritative; kubeadm cannot overwrite an existing
member. Wiping /var/lib/etcd on the broken node is NOT enough. The
stale member must be removed from the cluster first.
 
WARNING: with 3 members you can lose 1 and keep quorum (2 of 3). Do
NOT run this if 2 members are down; that needs an etcd snapshot restore.
 
STEP 1 - On a HEALTHY control plane (stpi-k8s-master or gcp-k8s-master),
list the etcd members:
 
# kubectl -n kube-system exec -it etcd-stpi-k8s-master -- etcdctl \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
    --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
    member list
 
Example output (IDs are examples):
<hex-id-1>, started, isu-k8s-cp,      https://172.18.0.101:2380, https://172.18.0.101:2379, false
<hex-id-2>, started, stpi-k8s-master, https://172.26.0.8:2380,   https://172.26.0.8:2379,   false
<hex-id-3>, started, gcp-k8s-master,  https://10.10.1.26:2380,   https://10.10.1.26:2379,   false
 
STEP 2 - Remove the stale member by its hex ID, verify, then delete
the old node object:
 
# kubectl -n kube-system exec -it etcd-stpi-k8s-master -- etcdctl \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
    --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
    member remove <STALE_MEMBER_HEX_ID>
 
Expected: Member <STALE_MEMBER_HEX_ID> removed from cluster
 
Run "member list" again: only stpi-k8s-master and gcp-k8s-master
should remain.
 
# kubectl delete node isu-k8s-cp
 
STEP 3 - On the BROKEN node (isu-k8s-cp), clean all state:
 
# kubeadm reset -f
# systemctl stop kubelet
# rm -rf /etc/kubernetes /var/lib/etcd /var/lib/kubelet /etc/cni/net.d
# systemctl restart crio
 
STEP 4 - On a healthy control plane, generate a fresh token and
certificate key:
 
# kubeadm token create --print-join-command
# kubeadm init phase upload-certs --upload-certs
 
STEP 5 - Rejoin the control plane on the broken node:
 
# sudo kubeadm join stage.proxyhost.lan:6443 \
    --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash> \
    --control-plane \
    --certificate-key <cert-key>
 
# kubectl get nodes
 
Why this works: removing the stale member restores quorum logic, and
the rejoin adds the node back cleanly with fresh certificates.
 
 
====================================================================
FAILURE CASE 2 - HOSTNAME CHANGED ON A NODE
====================================================================
 
Symptom: kubelet fails with: node "old-name" not found. The kubelet
credentials still belong to the old node name.
 
On the affected node:
 
# sudo systemctl stop kubelet
# sudo systemctl stop crio
# sudo rm -rf /etc/kubernetes /var/lib/etcd /var/lib/kubelet
 
Clear leftover kubelet mounts:
 
# sudo mount | grep /var/lib/kubelet | awk '{print $3}' | xargs -r sudo umount -l
# mount | grep /var/lib/kubelet || echo "All kubelet mounts cleared"
 
Confirm the services are stopped:
 
# sudo systemctl status kubelet crio
 
Update /etc/hosts with the NEW hostname and the floating IP entry:
 
127.0.0.1 <new-hostname>
::1       <new-hostname>
10.10.1.100 stage.proxyhost.lan
 
On a healthy control plane, remove the old node object and create a
fresh join command:
 
# kubectl delete node <old-hostname>
# kubeadm token create --print-join-command
 
Back on the node, restart the runtime and rejoin:
 
# sudo systemctl start crio
# sudo kubeadm join stage.proxyhost.lan:6443 \
    --token <token> \
    --discovery-token-ca-cert-hash sha256:<hash>
 
(or run: bash slave-nodes.sh)
 
 
====================================================================
FAILURE CASE 3 - FLOATING IP NOT FAILING OVER
====================================================================
 
Symptom: the VIP stays on a dead node, or appears on BOTH HAProxy
nodes (split-brain).
 
Which node holds the VIP?
# ip addr show eth0 | grep 10.10.1.100
 
Check Keepalived and HAProxy on both nodes:
# systemctl status keepalived haproxy
# journalctl -u keepalived --since "10 min ago"
 
Common causes to verify:
- VRRP (protocol 112) blocked by firewalld or a network ACL between
  the two HAProxy nodes
- Different virtual_router_id on the two nodes, or wrong
  unicast_src_ip / unicast_peer
- HAProxy nodes not in the same L2 segment
- HAProxy not running on the MASTER, so the health check keeps
  lowering its priority
 
 
====================================================================
FAILURE CASE 4 - GPU NOT DETECTED ON A NODE
====================================================================
 
Check the GPU Operator pods on the node:
# kubectl -n gpu-operator get pods -o wide | grep <gpu-node>
 
Confirm the driver sees the GPU (run on the GPU node):
# nvidia-smi
 
Confirm Kubernetes advertises it:
# kubectl describe node <gpu-node> | grep -A2 "nvidia.com/gpu"
 
Common causes to verify:
- Node is missing the node-pool=gpu label, or GPU workloads lack the
  matching toleration
- Kernel headers missing, or Secure Boot blocking the NVIDIA driver
  on the Ubuntu node
- Driver installed on the host AND operator-managed driver enabled at
  the same time (set driver.enabled=false if the host provides it)
- Container toolkit not configured for CRI-O on that node
 
 
====================================================================
FAILOVER BEHAVIOUR SUMMARY
====================================================================
HAProxy-1 (MASTER) down      -> Keepalived on HAProxy-2 takes the VIP,
                                no kubeconfig changes needed
HAProxy process crashes      -> health check fails, priority drops,
                                VIP moves to BACKUP
One control plane down       -> HAProxy removes it from the pool,
                                etcd keeps quorum (2 of 3)
MASTER recovers              -> higher priority reclaims the VIP
GPU node down                -> pods reschedule onto remaining GPU
                                nodes if capacity exists
